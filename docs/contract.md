# Offline timetable subset v1

Transit publishers supply five UTF-8 CSV files with exact column order as in fixtures/feed: stops.txt, trips.txt, calendar.txt, calendar_dates.txt and stop_times.txt. This is a deliberately small GTFS-shaped contract, not a complete GTFS validator. Full feeds with routes, agency, optional columns or frequencies must be adapted before import. Each file is at most 8 MB / 20,000 rows. All stop/trip/service identifiers are nonblank strings; trips reference a calendar service or an exception-only service. Stop references must exist. A trip needs at least two strictly increasing unique positive stop_sequence values; departure>=arrival at each stop, next arrival>=previous departure.

Calendar start/end dates use YYYYMMDD; both are inclusive. Seven weekday flags are 0/1, with Monday first. A calendar_dates row overrides that service/date: 1 adds, 2 removes. Service/date exceptions are unique. Times range 00:00:00 through 47:59:59; 24:12 is 12 minutes after midnight of the next civil day but belongs to the original service date. Queries use canonical YYYY-MM-DD service dates and include departures equal to --after. This baseline never converts timetable clocks to timezone/UTC instants, computes live delays, plans transfers or checks vehicle capacities.

Import builds a new SQLite archive with foreign keys and a departure index; CLI publishes it only after complete validation and refuses any existing database target. Failed imports leave the old target untouched. Direct import_feed into an empty database rolls back schema and rows on failure. Queries open archives read-only. The sample has three stops, two trips and five stop times; 2026-01-06/B returns T1 at 24:12; on Jan5 the weekday service is removed and T2 at 08:25 is added.

# Revision warehouse v1

`transit-feed revision-init --source-db BASE --db NEW` copies a legal archive produced by `import` into an independent revision warehouse. `BASE` and the original CSV files are never modified and may be removed after init. `NEW` must not exist (or be a symlink); initialisation validates BASE before publishing, and any failure leaves no NEW path. Success prints `{"known_seq":0}`. The old `import` and `departures` commands and the five baseline tables keep their exact behaviour; a revision archive also answers legacy `departures` queries.

`transit-feed revision-apply --db DB --file BATCH` accepts or rejects one JSON batch atomically. The top level is exactly `{"changes":[...]}` with a nonempty list, bounded by the shared 8 MB JSON input limit. Each `put` has exactly `op, correction_id, trip_id, stop_sequence, from, to, arrival, departure`; each `retract` has exactly `op, correction_id`. `correction_id`, `trip_id` are nonblank strings with no leading/trailing whitespace (max 200 chars); `stop_sequence` is a positive integer; `from`/`to` are canonical `YYYY-MM-DD` with `from<=to`; times use 00:00:00..47:59:59 and `arrival<=departure` within the entry. An ID may appear once per batch. The trip and stop sequence must exist in the baseline. A put may create an ID, replace that ID's version, or reactivate a retracted ID, but it can never change the ID's original trip/stop_sequence identity. Retracting an unknown or already retracted ID is an error. Revisions never add stops or edit baseline calendar data.

Acceptance sequence numbers belong to the warehouse: each successful batch receives previous+1, and a failed batch leaves no ID, version, derived data or sequence gap. Output is `{"known_seq":N}`. All changes of a batch are applied first; the whole batch is then validated against the final state. Every affected trip must be legal on every date in all its final segments, even when the service does not run that day: each stop has `arrival<=departure`, the next stop's arrival is at least the previous stop's departure, and both times stay within 00:00:00..47:59:59. Values revealed by retractions or shortened ranges (baseline or another ID's old value) take part in validation. If validation fails, nothing from the batch is stored and the sequence does not advance.

When several IDs cover the same trip/stop_sequence, the winning value is the whole arrival/departure pair of the candidate with the greatest `(accept_seq, correction_id)`; equal accept sequences are decided by the Unicode code-point order of the ID, so input array order never matters. The winner applies only where its date range covers the day; otherwise the baseline pair is used. Each ID contributes only its last state at or before the queried knowledge K; a retract state contributes nothing, and a newer put whose range excludes the day does not fall back to that ID's older version (an older K still shows the older version). Retracting one ID never restores an earlier put of the same ID but may reveal other IDs' or baseline values.

`transit-feed revised-departures --db DB --date DAY --stop STOP [--after HH:MM:SS] [--known-seq K]` is read-only and never creates a missing database. Running eligibility uses the baseline calendar and exception overrides. Revision selection happens before the inclusive `after` filter (default 00:00:00); omitted K means the current sequence, and an explicit K must be an integer from 0 to the current sequence (future K is an error). Unknown stops, non-canonical dates and malformed times are errors. Output is `{"known_seq":K,"departures":[...]}`; each item keeps the legacy `trip_id, stop_sequence, departure, service_date` fields and adds `correction_id` (`null` for baseline). Items sort by final departure seconds, `trip_id`, then `stop_sequence`; repeated visits of one trip to the same stop remain separate rows. Times of 24:xx stay attached to their original service date and are never converted to civil dates or UTC. An empty result still reports the actual K.

Storage and history: the warehouse adds three tables. `revision_state` holds the single current knowledge sequence. `revision_identity(correction_id PK, trip_id, stop_sequence)` fixes each ID's identity. `revision_version(correction_id, accept_seq, kind, from_day, to_day, arrival, departure, PK(correction_id,accept_seq))` stores immutable put/retract versions; a put keeps its date range, so no per-date rows are ever materialised and a century-wide range costs one row. Queries evaluate the last version per ID at K and compare date strings; old K answers are reproducible after restart because accepted versions are never edited, only appended. Deleting or rewriting version rows, changing `revision_state` outside `revision_apply`, or adding views/triggers breaks the invariant. Batch validation sweeps only the boundary dates introduced by the affected trip's revisions (range start and day after range end), so it covers every date segment without scanning days.

The same behaviour is available as a reusable Python API in `transit_feed`: `revision_init(source_db, new_db)`, `revision_apply(db, batch_or_path)` and `revised_departures(db, day, stop, after='00:00:00', known_seq=None)` returning the same dictionaries the CLI prints; invalid input raises `ValueError`.

# Regional warehouse v1

`transit-feed regional-init --feed KEY=DB [...] --interchanges CSV --db NEW` merges two to eight archives produced by `import` into one independent, read-only regional warehouse. Each `--feed` names a publisher `KEY` and its baseline archive. Keys are nonblank strings with no leading/trailing whitespace, are unique, and input paths must differ (symlink-aware). Only baseline archives are accepted; a revision warehouse, a bare or corrupt database, a view or a trigger is rejected. `NEW` must not exist and must not be a symlink; an existing path is preserved byte for byte. Inputs and the mapping are read only and never modified. The warehouse copies every stop, trip, service and time row needed for queries, so `NEW` keeps answering after the source archives and the CSV are deleted or moved. All archive, mapping and relational validation happens before publication; any failure leaves no `NEW` path, temporary file or newly created parent directory behind.

Identifiers are namespaced by `KEY`. A stop, trip or service named `S`, `T` or `WK` in one archive is a different object from the identically named one in another archive; they never join or overwrite each other. Local primary-key, foreign-key and calendar semantics of each source are preserved per publisher.

The mapping file is strict UTF-8 CSV (an optional UTF-8 BOM is tolerated) with exactly the header `feed_key,stop_id,interchange_id` and exactly three nonblank, unpadded fields per row. `feed_key` must be one of this run's keys and `stop_id` must exist in that key's archive. One source stop maps at most once, so repeated `(feed_key, stop_id)` rows are rejected; different publishers' stops and several stops of one publisher may share an `interchange_id`. Unknown keys, unknown stops, duplicate mappings, a wrong header, malformed/empty/padded rows, a non-UTF-8 file and unknown `interchange_id` values are rejected as a whole, and nothing is published. A publisher's unmapped stops never appear in regional results. An `interchange_id` with mappings but no eligible departure reports an empty `departures` list; an unregistered `interchange_id` is an error.

Running eligibility is decided per publisher from that publisher's own `calendar` and `calendar_dates`: inclusive start/end, Monday-first weekday flags, and type 1 add / type 2 remove exceptions overriding the weekday result. The calendar and exceptions of identically named services in different publications are never combined. Only after that per-publisher decision are that publisher's mapped stops selected for the requested interchange.

`transit-feed regional-departures --db DB --date DAY --interchange ID [--after HH:MM:SS]` is read-only and never creates a missing database. `DAY` is a canonical `YYYY-MM-DD` service date; `after` defaults to `00:00:00`, uses the same `00:00:00..47:59:59` format, and is inclusive. Times of 24:xx remain attached to the queried service date and are never converted to civil dates or UTC. Results sort by departure seconds, `feed_key`, `trip_id`, then `stop_sequence`; identical local trip names, equal departure times, two stops of one publisher mapped to the same interchange and repeated visits of one trip to an interchange all remain distinct rows and are never deduplicated.

Successful output is `{"service_date":DAY,"interchange_id":ID,"departures":[...]}`. Each departure has exactly `feed_key, trip_id, stop_sequence, departure, service_date`; `departure` uses the shared time format. Unknown interchanges, non-canonical dates, malformed `after` values, corrupt warehouses and missing databases are CLI exit code 2 on stderr; success prints JSON on stdout. The Python API `regional_init(feeds, interchanges_csv, new_db)` (with `feeds` as `{KEY: DB}`, `[(KEY, DB)]` or `["KEY=DB"]`) and `regional_departures(database, service_date, interchange_id, after='00:00:00')` return the same dictionaries and raise `ValueError` for invalid input.

Storage: the warehouse uses eight tables and no per-day materialisation. `regional_feed` lists the keys; `regional_stop`, `regional_trip`, `regional_calendar`, `regional_exception` and `regional_time` keep publisher-local rows keyed by `(feed_key, local id)` with composite foreign keys; `regional_interchange` and `regional_mapping` hold the published interchange view. `regional_time` keeps its primary key `(feed_key, trip_id, seq)`, so a trip's repeated visits stay separate and a local trip id is never merged across feeds. Queries open the archive read-only and add no views or triggers. This remains a single-operator local batch tool: no network service, multi-writer protocol or crash-recovery guarantee is implied.

Errors use CLI exit code 2 and write to stderr; successful commands print JSON to stdout. This remains a single-operator local batch tool: no network service, multi-writer protocol or crash-recovery guarantee is implied.

# Stop closure board v1

`transit-feed stop-board --db DB --closures FILE --date DAY --stop STOP [--after HH:MM:SS]` answers a service-day stop board from an unchanged timetable archive plus a separate closure plan. The archive and closure CSV are opened read-only; a query never creates or modifies the database, the closure file or any other path, and a missing database is an error rather than an empty archive. The board reuses the offline archive, adds no per-day closure storage and stays within the Python standard library.

The closure plan is a strict UTF-8 CSV (an optional UTF-8 BOM is tolerated) with exactly the header `closure_id,stop_id,from,to,reason` and exactly five fields per row. `closure_id` and `stop_id` are nonblank identifiers with no leading/trailing whitespace (max 200 chars, no control characters); `from`/`to` are canonical `YYYY-MM-DD` service dates with `from<=to` and both endpoints inclusive; `reason` is a nonblank description with no control characters. `closure_id` is unique across the file. `stop_id` must exist in the queried archive. Different notifications may cover the same stop with overlapping or identical date ranges: their identities and reasons are never merged, dropped or replaced. A wrong encoding, wrong header, missing/extra column, empty or padded field, duplicate ID, unknown stop, non-canonical or inverted date and an over-large file are rejected as a whole.

Planned departures follow the existing service-day rules for the requested `DAY`: the calendar start/end range is inclusive, weekday flags are Monday-first, and a `calendar_dates` type 1 add / type 2 remove exception overrides the weekday result. Exceptions decide which visits exist first; closure status is then applied only to the visits that actually exist. Each `(trip_id, stop_sequence)` visit is kept separately, so a trip visiting the same stop several times yields one row per visit. `--after` defaults to `00:00:00`, uses the shared `00:00:00..47:59:59` format and is inclusive; times of `24:xx` stay attached to the original service date and are never converted to civil dates or UTC.

A notification covers a visit when its `stop_id` equals the queried stop and `from<=DAY<=to`. On a closed day every planned visit at that stop keeps its identity but is `serviceable=false` and carries all matching closure IDs; a closure never removes visits of the same trip at other stops and never changes other stops' planned departures or service-day eligibility. On an open day the top level reports `closed=false` and each visit is `serviceable=true` with an empty `closure_ids`. A closed day on which the stop has no planned departures still reports `closed=true` with the matching notifications instead of an open status.

Closure ranges are evaluated by string comparison against the canonical service date; they are never expanded into one row per day, so a multi-year range costs the same as a one-day range. Only the last-read file contents are used, so updating the plan is reflected by the next query.

Successful output is a JSON object with exactly `service_date`, `stop_id`, `closed`, `closure_ids`, `closures` and `departures`. `closure_ids` lists every closure ID matching this stop and service day in Unicode code-point order, and `closures` lists those same notifications in the same order with only `closure_id` and `reason`. `departures` sorts by final departure seconds, `trip_id`, then `stop_sequence`; each item has exactly `trip_id`, `stop_sequence`, `departure`, `service_date`, `serviceable` and `closure_ids`. Unknown stops, non-canonical dates, malformed `after` values, missing/corrupt archives and missing/invalid closure files raise `ValueError` in the Python API and exit code 2 on stderr in the CLI; success prints JSON on stdout.

The reusable Python API is `transit_feed.stop_board(database, closures_csv, service_date, stop, after='00:00:00')`, returning the same dictionary as the CLI.

# Vehicle duty check v1

`transit-feed duty-check --db DB --duties DUTIES.csv --links LINKS.csv --from DAY --to DAY` answers whether a dispatcher's vehicle duty plan is executable against an archive produced by `import`. The database is opened read-only and must be a legal import archive: revision warehouses, regional warehouses, foreign schemas, views, corrupt files and missing paths are rejected. Trips that no duty row mentions are outside the plan and are never reported as unassigned or missing. The same behaviour is available as `transit_feed.duty_check(database, duties_file, links_file, from_date, to_date)`, returning the same dictionary the CLI prints.

The duty CSV has exactly the header `vehicle_id,trip_id,start_date,end_date` and four fields per row. Each row assigns the instances of `trip_id` that run on every day of the inclusive `start_date..end_date` range to `vehicle_id`. Both dates are canonical `YYYY-MM-DD` with `start_date<=end_date`; `trip_id` must exist in the archive. `vehicle_id` is nonblank, has no leading/trailing whitespace and no control characters, but is otherwise an opaque identity and is never trimmed. The link CSV has exactly the header `from_stop,to_stop,seconds` and three fields per row. Both stops must exist; `seconds` is a decimal non-negative integer string no greater than 86400; one directed stop pair appears at most once, while the reverse direction is a separate row that must be supplied explicitly. A same-stop pair with no explicit row defaults to 0 seconds; a different-stop pair with no row is not resolved through multi-hop paths and is a missing rule. Both files are strict UTF-8 (an optional BOM is tolerated), reject any malformed or padded row and any wrong column count, are limited to 8,000,000 bytes and 20,000 data rows, and a header-only file is legal.

Running eligibility is decided per service day by the archive's calendar and `calendar_dates` exceptions with the same semantics as every other query: the calendar range is inclusive, weekday flags are Monday-first, and a type 1 exception adds a day while a type 2 exception removes it, overriding the weekday result. Exceptions apply even to services that only appear in `calendar_dates`, and an exception on a day outside the service's calendar range still adds that day. A duty row contributes an instance only where its trip runs; a rule overlap on a day when the trip does not run creates neither an instance nor a duplicate. When two or more rows claim the same `trip_id`/service-date instance, one `duplicate_assignment` is reported per instance even if the rows are identical or name the same vehicle, and that instance is removed from every vehicle chain instead of being assigned to an arbitrary vehicle. Other uniquely assigned instances are still checked normally. Instances that are not assigned are never backfilled.

Occupancy runs from the first stop's `departure` to the last stop's `arrival`, with the stops chosen by `stop_sequence` rather than by input row order. A zero-duration occupancy is allowed, and the first stop's arrival and last stop's departure never widen the interval. Instances are ordered across service days by absolute time: the service-day ordinal times 86400 plus the timetable seconds. A `24:xx` time therefore stays attached to its own service date and is never relabelled onto the following one, and because clocks reach 47:59:59 an instance of a neighbouring service day can sort between two instances of the queried day. The reported identity always keeps the original `service_date` and the `24:xx`..`47:xx` string.

For each vehicle the uniquely assigned instances form one chain ordered by absolute start time, absolute end time, `trip_id`, then `service_date`; each adjacent pair in that chain is checked exactly once, with no enumeration of non-adjacent combinations. `available_seconds` is `next.start - previous.end` on the absolute clock. If it is negative the problem is `overlap` and `shortfall_seconds` is its absolute value while `required_seconds` is null. Otherwise, if the directed terminal rule is missing, the problem is `missing_link` with both `required_seconds` and `shortfall_seconds` null. Otherwise, if `available_seconds` is smaller than the rule, the problem is `insufficient_turnaround` with `shortfall_seconds` equal to the difference; equality means the connection is feasible and produces nothing. An overlap takes precedence over a missing rule, and a pair yields at most one problem.

`--from`/`--to` name an inclusive service-day range that decides which problems are *reported*, not which instances exist. The whole valid duty CSV is read and every chain is built from all instances: an out-of-range instance still bounds its in-range neighbours, and one instance on each side of the window is retained so a long gap is not hidden. A duplicate is reported only when its service date falls in the range, and an adjacent pair is reported when at least one end's service date falls in the range. An instance whose absolute time spills into the next civil day is still judged by its original `service_date`, so a `24:xx` instance belonging to the previous service day is never cut off by the queried day's midnight.

Successful output has exactly `feasible`, `duplicate_assignments` and `connections`. `feasible` is true exactly when both arrays are empty; a business conflict is still a successful query and exits 0. Each duplicate has exactly `kind` (always `duplicate_assignment`), `trip_id`, `service_date`, `vehicle_ids` (deduplicated and sorted vehicle identities) and `rule_rows` (ascending data-row numbers, counting the header as row 1). Duplicates sort by `service_date` then `trip_id`. Each connection has exactly `kind`, `vehicle_id`, `previous`, `next`, `available_seconds`, `required_seconds` and `shortfall_seconds`; `previous` and `next` each have exactly `trip_id`, `service_date`, `start_stop`, `end_stop`, `start` and `end`, with `start`/`end` the original service-day `HH:MM:SS` strings. Connections sort by `vehicle_id`, the next absolute start, the previous absolute start, `next.trip_id`, `previous.trip_id`, then `next.service_date` and `previous.service_date`. Seconds are integers, or null exactly where the contract says so; overlaps are never normalised to zero.

Every call reads the archive and both CSVs afresh, so a file rewritten in place between two calls in the same Python process — even at the same path and size — is reflected by the next call, and no cached eligibility, chain or link value can leak across calls. A failed query and a successful one alike create or modify no database, directory, temporary file, log, cache or result file; output travels only through the return value or stdout/stderr. Invalid dates, unknown trips or stops, duplicate directed rules, malformed or over-large CSVs, bad encodings and missing, corrupt or non-import archives raise `ValueError` (or the corresponding `OSError`/`sqlite3.Error`); the CLI prints the reason on stderr, leaves stdout empty and exits 2 without partial results. All rows are validated even when the queried range selects no instance.

# Group booking workbench v1

`transit-feed booking-init --source-db BASE --capacities FILE --db NEW` copies a legal archive produced by `import` into an independent booking workbench. Only the five-table baseline archive is accepted; revision warehouses, regional warehouses, existing booking workbenches, foreign schemas, views, triggers, corrupt files and missing paths are rejected. `BASE` is opened read-only and never modified. `NEW` must not exist and must not be a symlink; an existing file or symlink is preserved byte for byte. All archive, CSV and relational validation finishes before publication, so a failure leaves no `NEW` path or temporary file. Success prints `{"trips":N,"bookings":0}`; afterwards the workbench answers with `BASE` and the capacity CSV deleted or moved, because the timetable, calendar, exceptions and capacities are all copied.

The capacity file is a strict UTF-8 CSV (an optional UTF-8 BOM is tolerated) with the exact header `trip_id,seats`. Every trip in `BASE` has exactly one row: a missing trip, a duplicated trip or an unknown `trip_id` rejects the whole file, and identifiers are matched exactly with no trimming. Each row has exactly two fields; `seats` is ASCII decimal digits only (`[0-9]+`, leading zeros allowed) whose value is between 0 and 10000. A wrong encoding, a wrong header, a missing or extra column, an empty/non-numeric/negative/fractional value and an out-of-range value are all rejected before anything is published. The capacity applies to every operating service day of that trip.

`transit-feed booking-create --db DB --file REQUEST.json` (or `booking_create(database, request)` with a Python dictionary) routes one group request atomically. The request object contains exactly `booking_id, origin, destination, service_date, earliest, latest_arrival, party_size, max_transfers, min_transfer_seconds`. `booking_id` is a nonempty string with no leading/trailing whitespace and no U+0000..U+001F or U+007F characters. `origin` and `destination` are two different existing `stop_id`s, matched exactly. `service_date` is canonical `YYYY-MM-DD`. `earliest` and `latest_arrival` use `00:00:00..47:59:59` strings with `earliest <= latest_arrival`; both boundaries are inclusive. `party_size` is an integer 1..10000, `max_transfers` an integer 0..3 and `min_transfer_seconds` an integer 0..3600. Booleans, floats and numeric strings are rejected for every numeric field (`True` is not 1). The CLI JSON must be a UTF-8 object with no duplicate keys and no missing or extra fields.

Only trip instances actually operating on `service_date` are used: the calendar weekday flags and the type 1 add / type 2 remove exceptions follow the same semantics as every other command, and times of `24:xx..47:xx` stay attached to that service day instead of borrowing the previous or next day's instance. Each ride leg is uniquely `(trip_id, board_sequence, alight_sequence)`; both sequences must exist and board must precede alight. Sequences need not be contiguous and are never used as array indices. Boarding time is the visit's `departure` and alighting time its `arrival`; when a trip visits one physical stop repeatedly, every visit keeps its own sequence identity. The first leg boards at `origin` at or after `earliest`; the last leg alights at `destination` at or before `latest_arrival`. Adjacent legs transfer at one identical `stop_id` (no walking), with the next leg's departure at least the previous arrival plus `min_transfer_seconds`; equality is allowed. A journey has at most `max_transfers+1` legs, and one `trip_id` is used at most once per journey. Passing an intermediate stop while staying on the same leg is not a transfer.

Seats are managed per `(trip_id, service_date, adjacent sequence pair)`, where adjacent means two consecutive visits after sorting that trip's visits by sequence. A leg riding from sequence `a` to sequence `b` needs at least `party_size` free seats on every adjacent segment it covers, and a successful booking holds all of them together. Capacity is never deducted once per whole trip: an `a..b` group and a `b..c` group may reuse the same seats, while the usage of every segment is the sum of `party_size` over all non-cancelled successful bookings covering it and can never exceed the trip's capacity. A group is never split across routes, trips or partial headcounts.

Among all complete journeys that fit the whole group under every active booking, the best is chosen by: (1) earliest final arrival in seconds; (2) fewest ride legs; (3) lexicographic comparison of the per-leg `(trip_id, board_sequence, alight_sequence)` tuples in ride order, with `trip_id` compared by Unicode code point and sequences as integers. The search enumerates every feasible journey rather than only the capacity-blind best: when the otherwise best route lacks seats, the next best is considered, and a prefix that reaches a transfer later but uses fewer legs is retained because it may be the only prefix that still fits the transfer limit. The retained labels per stop are non-dominated in `(arrival, leg count, used trips)`, keeping the lexicographically smallest leg tuple for equal keys.

Success or failure returns exactly `booking_id, accepted, party_size, service_date, arrival, legs`. On success `accepted` is true, `arrival` is the final `HH:MM:SS`, and `legs` lists, in ride order, objects with exactly `trip_id, board_sequence, alight_sequence, from_stop, to_stop, departure, arrival`. When no complete journey with seats exists, `accepted` is false, `arrival` is null and `legs` is `[]`; this is a normal business result that exits 0, leaves no partial legs, no seat deduction and no occupied `booking_id`, and the same ID may be retried afterwards.

Identity lifecycle: a successful `booking_id` is permanently bound to every field of its first request and to its original receipt. Repeating `booking-create` with the same ID and the same request returns the stored receipt without rerouting or re-seating, even after the booking has been cancelled (JSON object key order is irrelevant). Reusing a successful ID with any changed request field is an error, even when cancelled and even when the new request has no feasible journey. The complete request is validated before any identity lookup, so an invalid request never reports an identity conflict; only brand-new IDs run the current seat search.

`transit-feed booking-cancel --db DB --booking ID` releases every segment of an active booking in one transaction and permanently keeps the original request and receipt, returning `{"booking_id":"ID","cancelled":true}`. Repeating the cancel returns the same result without releasing anything again, so occupancy can never go negative or exceed capacity; an unknown ID is an error. `transit-feed booking-show --db DB --booking ID` returns exactly `{"booking_id":"ID","status":"active|cancelled","receipt":<original receipt>}` for a known ID and errors on an unknown ID; it is strictly read-only. Identity conflicts, cancellation status, original receipts and seat commitments all survive a Python process restart. Each create or cancel commits as one SQLite transaction, so an interrupted process can never expose partial rows or partial occupancy, and a caller that misses the receipt can safely replay the same ID. This is a single-operator local workbench: no network service, multi-writer protocol or waitlist is provided.

Storage adds four tables to the copied baseline. `booking_capacity(trip_id PK, seats)` fixes one capacity per trip. `booking(booking_id PK, request_json, receipt_json, status)` keeps the immutable request, the original receipt and `active`/`cancelled`. `booking_leg(booking_id, leg_index, trip_id, service_date, board_seq, alight_seq, from_stop, to_stop, departure, arrival, party_size)` records every promised leg in ride order. `booking_occupancy(trip_id, service_date, from_seq, to_seq, used, PK(trip_id, service_date, from_seq, to_seq))` holds one positive usage total per adjacent segment; rows disappear when usage returns to zero. Opening a workbench revalidates table layout, integrity, foreign keys, capacity coverage and the invariant that stored occupancy equals the sum of active legs, so a hand-edited or corrupt database is rejected. A missing database is never created; validation, routing or commit failures never change existing active bookings. The reusable Python API is `transit_feed.booking_init(source_db, capacities_csv, new_db)`, `booking_create(database, request)`, `booking_cancel(database, booking_id)` and `booking_show(database, booking_id)`, returning the same JSON-serialisable dictionaries as the CLI and raising `ValueError` (or the corresponding `OSError`/`sqlite3.Error`) on invalid input; the CLI exits 2 with the reason on stderr and empty stdout, and every successful command prints exactly one JSON object on stdout.

# Punctuality report ledger v1

`transit-feed punctuality-init --db NEW` creates an independent SQLite ledger for actual-arrival punctuality reports. `NEW` must not exist and must not be a symlink; an existing path is preserved byte for byte and a failed initialisation leaves no `NEW` path, temporary file or newly created parent directory. Success prints `{"reports":0}`. The other three commands never create a missing ledger, never convert another SQLite database into one, and reject anything whose table set or schema marker does not match the ledger created here. `punctuality-show` opens the ledger strictly read-only and begins no write transaction.

The schedule source (`--db` on `punctuality-report`) is opened read-only and may be either the five-table archive produced by `import` or a revision warehouse produced by `revision-init`; regional and booking warehouses and foreign schemas are rejected. A baseline archive always uses knowledge sequence 0; an explicit nonzero `known_seq` on a baseline archive is an error. On a revision warehouse an omitted `--known-seq` resolves to the current knowledge sequence at the start of the call, and an explicit value must be an integer from 0 through that current sequence. One report uses exactly one fixed knowledge snapshot: the final effective `arrival` of every planned visit is chosen for that sequence and the report's service date, applying only the latest state of each correction at or below the sequence when its date range covers the day.

## Observation CSV

The observation file is strict UTF-8 (an optional UTF-8 BOM is tolerated) with the exact header `event_id,trip_id,service_date,stop_id,observed_arrival` and exactly five fields per data row. It is bounded by 8,000,000 bytes and 20,000 data rows; a header-only file is legal and yields an all-zero report with an empty `trips` list. Every identifier is a nonempty string with no leading/trailing whitespace or control characters and is matched exactly with no silent trimming. `event_id` is unique across the whole file. `trip_id` and `stop_id` must exist in the schedule archive; an unknown trip or stop rejects the whole file. `service_date` must be a canonical `YYYY-MM-DD` date inside the inclusive `--from..--to` range; `--from` must not be later than `--to` and both dates are canonical. `observed_arrival` uses the shared service-day clock `00:00:00..47:59:59`; times of 24:xx..47:xx stay attached to the given service date and are never converted to civil dates or UTC. Wrong encoding, wrong header, wrong column count, empty or padded fields, duplicate event ids, non-canonical or out-of-range dates, malformed times and over-large files are rejected as a whole; every row is validated even when the result would otherwise be empty or the service does not run, so no error row is skipped because of an empty result.

Each `(service_date, trip_id)` pair present in the CSV is one reported trip instance. Trips with not even one observation are never enumerated. All events of one trip are processed together, ordered by observed-arrival seconds and then by the Unicode code-point order of `event_id`. Planned visits are ordered by `stop_sequence`.

## Global pairing and tie rules

Within one trip instance every observed event pairs with at most one planned visit and every planned visit with at most one observed event; only an event and a visit with the same `stop_id` may pair, and the pairing must preserve the order of both sequences independently (a standard order-preserving sequence alignment). The chosen pairing is globally optimal, never a row-by-row nearest-time greedy match, under this exact ranking: (1) maximise the number of pairs; (2) among maximum-cardinality pairings minimise the sum of `abs(observed_arrival - scheduled_arrival)` over all pairs; (3) among still-tied pairings choose the lexicographically smallest list of `(event_id, stop_sequence)` pairs written in observation order, with `event_id` compared by Unicode code point and `stop_sequence` as an integer. The rule therefore handles repeated visits to the same stop, missing middle events, observed events at stops the trip never serves (they can never pair and are listed as unmatched observations) and several events at the same timestamp deterministically; identical inputs and knowledge snapshot always produce the identical pairing.

The deviation is observed minus scheduled in seconds. A deviation strictly smaller than `-early_tolerance` is `early`; strictly greater than `late_tolerance` is `late`; both threshold boundaries, including zero deviation under zero tolerances, are `on_time`. Both tolerances are integers from 0 through 86400. The CLI accepts ASCII decimal digits only; the Python API rejects booleans, floats and numeric strings for tolerances and `known_seq` alike (`True` is never accepted as 1). Unpaired planned visits are missed visits; unpaired observed events are listed separately and never contribute to the matched/early/on_time/late counts. When a trip does not run on the named service date (calendar weekday flags plus type 1 add / type 2 remove exceptions), the trip still appears with `service_active=false`, an empty planned visit list and every observed event unmatched; no other service date's plan is ever substituted and the events are never silently dropped.

## Report body

Successful generation, review and read return the same report body, whose top level contains exactly `report_id`, `review_of`, `known_seq`, `summary` and `trips`. An initial report has `review_of` null; a review carries the referenced initial report id. `summary` contains exactly the integer counters `scheduled_visits`, `matched_visits`, `on_time`, `early`, `late`, `missed_visits` and `unmatched_observations`, summed over every trip in the report. `trips` is sorted by `(service_date, trip_id)`; each item contains exactly `service_date`, `trip_id`, `service_active`, `matched`, `missed` and `unmatched_observations`. `matched` is sorted by `stop_sequence` and each item contains exactly `event_id`, `stop_sequence`, `stop_id`, `scheduled_arrival`, `observed_arrival`, `deviation_seconds`, `status` and `confirmed`; time fields use canonical `HH:MM:SS`, sequences and seconds are integers, `status` is one of `early`/`on_time`/`late`, and `confirmed` is a boolean that is true only for pairs explicitly confirmed by this review's decisions file (always false on an initial report). `missed` is sorted by `stop_sequence` with exactly `stop_sequence`, `stop_id` and `scheduled_arrival`. `unmatched_observations` is sorted by observed-arrival seconds then `event_id`, with exactly `event_id`, `stop_id` and `observed_arrival`.

## Human review and recomputation

`transit-feed punctuality-revise --reports LEDGER --base BASE_ID --report ID --decisions FILE` only references a saved **initial** report in the same ledger. Multiple independent reviews may target the same initial report, but a review can never be the base of another review. The decisions file is UTF-8 JSON whose top level contains exactly `confirmations`, a nonempty array; each item contains exactly the string `event_id` and a positive integer `stop_sequence` (a boolean is not an integer). Duplicate JSON keys, duplicate confirmation pairs, unknown events, non-positive or non-integer sequences, extra or missing fields, and non-string event ids reject the whole review. A confirmation is located in the original report of the event's own trip: the trip must actually run, the stop sequence must exist there, and the visit's `stop_id` must equal the observed event's `stop_id`. One batch must never reuse the same observed event or the same planned visit twice, and the confirmed pairs must not invert the relative order of either side within that trip; if any item is invalid or the whole batch cannot hold simultaneously, the entire review is rejected, no existing report changes and the new id is never occupied.

A review keeps the initial report's observed events, running eligibility, effective planned arrival times, knowledge sequence and both tolerances, so the review completes even after the source schedule archive and the original observation CSV have been updated, moved or removed. For every trip touched by a confirmation the global pairing is recomputed under the same priority rules, but every confirmed pair must appear in the result and only pairings containing all confirmed pairs compete; the other pairs may change as a consequence rather than only the confirmed row being edited. Trips without a confirmation keep their original pairing and classification exactly. Missed visits, unmatched observations and all summary counters are recomputed from the final pairing. A confirmation only decides which event belongs to which visit; the status is still classified honestly against the original tolerances, so a confirmed pair can be `early` or `late`.

## Identity, replay and storage

`report_id` is a nonempty string without leading/trailing whitespace or control characters and is permanently unique within one ledger across both generation methods. The initial request identity contains: the method marker; the schedule archive path and the observation CSV path converted against the working directory to absolute paths with normalised separators and dot segments (symlinks are not resolved and the targets need not exist when identities are compared); the SHA-256 of the raw CSV bytes; the inclusive date range; both tolerances; and whether the knowledge sequence was explicit together with the specified value. The ledger path is only the address of the ledger and is never part of a request identity. Repeating an initial report with the same id and the same request identity returns the stored report without reopening the schedule archive and without replacing an originally omitted knowledge sequence with the current value; the CSV must still be readable so its raw bytes can be re-hashed. Reusing the same id with any changed identity field is an error. The review request identity contains the review marker, the initial report id and the complete set of confirmation pairs; the decisions file path, JSON key order and array ordering never affect it. An input or computation failure never occupies an id.

The ledger uses two tables. `punctuality_meta(key, value)` stores the schema marker. `punctuality_report(report_id PK, kind, review_of, request_json, report_json, facts_json)` stores, for every initial and review report, the canonical request identity, the returned report body and the historical facts (ordered observations, effective planned visits, running eligibility, tolerances and the knowledge sequence) required to recompute a review later. The report body, its request identity and its review facts are committed in one SQLite transaction, so an interrupted process can never expose partial results. The reusable Python API is `transit_feed.punctuality_init(report_database)`, `punctuality_report(schedule_database, report_database, report_id, observations_csv, from_date, to_date, known_seq=None, early_tolerance=60, late_tolerance=300)`, `punctuality_show(report_database, report_id)` and `punctuality_revise(report_database, base_report_id, report_id, decisions_file)`, each returning the same JSON-serialisable dictionary the CLI prints. Invalid input raises `ValueError` (or the corresponding `OSError`/`sqlite3.Error`); the CLI exits 2 with the reason on stderr and empty stdout, and every successful command prints exactly one JSON object on stdout. The schedule archive, observation CSV and decisions file are all opened read-only and must never point at the writable ledger; no result copies, caches or logs are created in other locations. This remains a single-operator local batch tool: no network service, multi-writer protocol or crash-recovery guarantee beyond the commit transaction is implied.
