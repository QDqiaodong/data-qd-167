# Offline timetable subset v1

Transit publishers supply five UTF-8 CSV files with exact column order as in fixtures/feed: stops.txt, trips.txt, calendar.txt, calendar_dates.txt and stop_times.txt. This is a deliberately small GTFS-shaped contract, not a complete GTFS validator. Full feeds with routes, agency, optional columns or frequencies must be adapted before import. Each file is at most 8 MB / 20,000 rows. All stop/trip/service identifiers are nonblank strings; trips reference a calendar service or an exception-only service. Stop references must exist. A trip needs at least two strictly increasing unique positive stop_sequence values; departure>=arrival at each stop, next arrival>=previous departure.

Calendar start/end dates use YYYYMMDD; both are inclusive. Seven weekday flags are 0/1, with Monday first. A calendar_dates row overrides that service/date: 1 adds, 2 removes. Service/date exceptions are unique. Times range 00:00:00 through 47:59:59; 24:12 is 12 minutes after midnight of the next civil day but belongs to the original service date. Queries use canonical YYYY-MM-DD service dates and include departures equal to --after. This baseline never converts timetable clocks to timezone/UTC instants, computes live delays, plans transfers or checks vehicle capacities.

Import builds a new SQLite archive with foreign keys and a departure index; CLI publishes it only after complete validation and refuses any existing database target. Failed imports leave the old target untouched. Direct import_feed into an empty database rolls back schema and rows on failure. Queries open archives read-only. The sample has three stops, two trips and five stop times; 2026-01-06/B returns T1 at 24:12; on Jan5 the weekday service is removed and T2 at 08:25 is added.

# Revision warehouse v1

`transit-feed revision-init --source-db BASE --db NEW` copies a legal archive produced by `import` into an independent revision warehouse. `BASE` and the original CSV files are never modified and may be removed after init. `NEW` must not exist (or be a symlink); initialisation validates BASE before publishing, and any failure leaves no NEW path. Success prints `{"known_seq":0}`. The old `import` and `departures` commands and the five baseline tables keep their exact behaviour; a revision archive also answers legacy `departures` queries.

`transit-feed revision-apply --db DB --file BATCH` accepts or rejects one JSON batch atomically. The top level is exactly `{"changes":[...]}` with a nonempty list, bounded by the shared 8 MB JSON input limit. Each `put` has exactly `op, correction_id, trip_id, stop_sequence, from, to, arrival, departure`; each `retract` has exactly `op, correction_id`. `correction_id`, `trip_id` are nonblank strings with no leading/trailing whitespace (max 200 chars); `stop_sequence` is a positive integer; `from`/`to` are canonical `YYYY-MM-DD` with `from<=to`; times use 00:00:00..47:59:59 and `arrival<=departure` within the entry. An ID may appear once per batch. The trip and stop sequence must exist in the baseline. A put may create an ID, replace that ID's version, or reactivate a retracted ID, but it can never change the ID's original trip/stop_sequence identity. Retracting an unknown or already retracted ID is an error. Revisions never add stops or edit baseline calendar data.

Acceptance sequence numbers belong to the warehouse: each successful batch receives previous+1, and a failed batch leaves no ID, version, derived data or sequence gap. Output is `{"known_seq":N}`. All changes of a batch are applied first; the whole batch is then validated against the final state. Every affected trip must be legal on every date in all its final segments, even when the service does not run that day: each stop has `arrival<=departure`, the next stop's arrival is at least the previous stop's departure, and both times stay within 00:00:00..47:59:59. Values revealed by retractions or shortened ranges (baseline or another ID's old value) take part in validation. If validation fails, nothing from the batch is stored and the sequence does not advance.

When several IDs cover the same trip/stop_sequence, the winning value is the whole arrival/departure pair of the candidate with the greatest `(accept_seq, correction_id)`; equal accept sequences are decided by the Unicode code-point order of the ID, so input array order never matters. The winner applies only where its date range covers the day; otherwise the baseline pair is used. Each ID contributes only its last state at or before the queried knowledge K; a retract state contributes nothing, and a newer put whose range excludes the day does not fall back to that ID's older version (an older K still shows the older version). Retracting one ID never restores an earlier put of the same ID but may reveal other IDs' or baseline values.

`transit-feed revised-departures --db DB --date DAY --stop STOP [--after HH:MM:SS] [--known-seq K]` is read-only and never creates a missing database. Running eligibility uses the baseline calendar and exception overrides. Revision selection happens before the inclusive `after` filter (default 00:00:00); omitted K means the current sequence, and an explicit K must be an integer from 0 to the current sequence (future K is an error). Unknown stops, non-canonical dates and malformed times are errors. Output is `{"known_seq":K,"departures":[...]}`; each item keeps the legacy `trip_id, stop_sequence, departure, service_date` fields and adds `correction_id` (`null` for baseline). Items sort by final departure seconds, `trip_id`, then `stop_sequence`; repeated visits of one trip to the same stop remain separate rows. Times of 24:xx stay attached to their original service date and are never converted to civil dates or UTC. An empty result still reports the actual K.

Storage and history: the warehouse adds three tables. `revision_state` holds the single current knowledge sequence. `revision_identity(correction_id PK, trip_id, stop_sequence)` fixes each ID's identity. `revision_version(correction_id, accept_seq, kind, from_day, to_day, arrival, departure, PK(correction_id,accept_seq))` stores immutable put/retract versions; a put keeps its date range, so no per-date rows are ever materialised and a century-wide range costs one row. Queries evaluate the last version per ID at K and compare date strings; old K answers are reproducible after restart because accepted versions are never edited, only appended. Deleting or rewriting version rows, changing `revision_state` outside `revision_apply`, or adding views/triggers breaks the invariant. Batch validation sweeps only the boundary dates introduced by the affected trip's revisions (range start and day after range end), so it covers every date segment without scanning days.

The same behaviour is available as a reusable Python API in `transit_feed`: `revision_init(source_db, new_db)`, `revision_apply(db, batch_or_path)` and `revised_departures(db, day, stop, after='00:00:00', known_seq=None)` returning the same dictionaries the CLI prints; invalid input raises `ValueError`.

Errors use CLI exit code 2 and write to stderr; successful commands print JSON to stdout. This remains a single-operator local batch tool: no network service, multi-writer protocol or crash-recovery guarantee is implied.
